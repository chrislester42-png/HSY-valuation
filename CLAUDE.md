# Rules for this project

This is a two-person FIN 5370 team project: an interactive equity valuation site for [COMPANY] ([TICKER]), built one section per module.

## Layout
- `research/` is the team's Obsidian vault (the team opens that folder, not the repo root, in Obsidian). Layout: `00 Project Home.md` (the map; keep its lists current), `01 Sources/` (one note per primary document, files in `_files/`), `02 Atomic Notes/` (one fact per note), `03 Drafts/` (milestone memos in progress), `04 Final Deliverables/` (submitted versions), `05 Questions/`, `06 Templates/` (copy these for every new note; fill the date yourself), `07 Daily/` (optional session notes).
- `workbook/` holds the team's Q&D workbook, one .xlsx saved from Excel. It is the only source of financial numbers for the site.
- `site/` is the published site: plain HTML, CSS, and JavaScript. No build step, no frameworks, no package installs. Libraries only from a CDN, and only when asked.
- `site/content.js` holds the words for each section. `site/data/financials.js` holds the numbers and is generated by `scripts/workbook_to_data.py`. `site/data/notes.js` holds the vault for the Knowledge Bank page and is generated by `scripts/build_vault.py`. `site/data/ailog.js` holds `AI Log.md` for the Process section and is generated by `scripts/ai_log_to_data.py`. Never hand-edit a generated file.
- The Knowledge Bank page (`site/vault.html`, `vault.css`, `vault.js`) is finished: a graph of the vault, like Obsidian's graph view. Do not change those three files, except what the Module 3 redesign brief allows (vault.html loads styles.css and the fonts; vault.css uses the shared colour variables and fixes its own contrast); the team sets its topic chips in the vault object of `site/content.js`.

## Sections and their modules
thesis (1) · financials (2) · vault, shown as "Knowledge Bank" on its own page, site/vault.html (3) · valuation (4) · theCall (5) · risks and catalysts, two sections, both Module 6 (6), built from a short research run filed into the vault: Risks lists what could hurt the call, each with dated facts and our take; Catalysts lists dated events in the next twelve months that could move the value, and three tripwires, each a published number with a threshold and what we would do · process (7), from the AI Use Evaluation Memo and the AI Log: each module's AI task and verdict, the failure modes found, and what we will change
Sections not yet built show "Coming in Module N." Touch only the section the current task names.

## Notes
- Every new note starts from the matching template in `research/06 Templates`. Keep the frontmatter keys exactly; fill `date-created` or `date-accessed` with today's date.
- Source note frontmatter: `type: source`, `id` (S1, S2, ... unique, never reused), `publisher`, `publication-date`, `date-accessed`, `url` or `file`.
- Atomic note frontmatter: `type: atomic`, `tags`, `status` (`needs-verification` until a person has checked the figure against the source, then `confirmed`; `unverified` if it cannot be checked; `partial`), `tier` (R, D, or E), `sources` (wiki-links to source notes).
- One fact per atomic note. The title is the fact in a few words with the figure. Filenames must not contain `$ % / : ?`.
- Link notes with `[[01 Sources/Note name]]` and `[[02 Atomic Notes/Note name]]`. Never rename a note without updating every link to it.
- After creating notes, add them to the right list in `00 Project Home.md`.
- The chain: every number on the site points at an atomic note (`note` field in the Fact); every atomic note points at a source note. Module 3 bakes this chain into the Knowledge Bank page.

## Workbook
- Detail Data is the only tab Module 2 fills. The team fills the WACC calculation tab by hand in Module 3, following Dr. Payne's videos; read it, never write into it. The DCF 1-Pager belongs to Module 4; leave it alone until then.
- Write into the workbook only with `python3 scripts/fill_workbook.py` (values in a temporary `fill.json`; the script's header shows the format). It rewrites only the cells you name and copies the charts, images, formulas, and other sheets through unchanged. Never use openpyxl or any library that re-saves the whole file (that drops the charts and images), never hand-edit the file's XML, and never use screen control to type into Excel. The workbook must be closed in Excel when the script runs.
- Write only into input cells, the ones that hold typed numbers. Never write into a cell that holds a formula and never change a formula.
- Dollars in millions to one decimal, shares in millions, as the row labels say.
- Actual columns (C and D) come from the company's filings through `python3 scripts/fill_detail_data_from_edgar.py` (the SEC's XBRL company facts, 10-K values; run it with `--dry-run` first, then with `--report "research/03 Drafts/Module 2 - Data pull.md"`, then make the verification form with `python3 scripts/verification_form.py`). It writes through `fill_workbook.py`, skips formula cells, and lists the cells the feed cannot supply; the person types those from the 10-K. Never run the older quarterly-layout script of the same name on the annual workbook.
- Forecast columns (E to G) are typed by the person, by hand, from FactSet's consensus estimates. Do not fill them and do not ask for a FactSet file; when asked, read them back and flag blanks or likely typing errors without changing anything.
- After every fill the user opens the workbook in Excel and saves it; that is when the formulas recalculate. The converter refuses to run until they have, so never work around its refusal.
- The person verifies the actual-year figures on a Word form made by `python3 scripts/verification_form.py` (every row prefilled from the workbook; they type the page and Y or N). Never fill that form in for them, and never mark a figure checked.

## Numbers
- Every number on the site traces to an atomic note in `research/02 Atomic Notes`, and through it to a source note. If a number has no note, do not write it; list it under "Numbers we still need" and tell the user.
- The exception is the numbers the Financials, Valuation, and The Call sections read from `site/data/financials.js`: those trace to the workbook. The workbook has its own source note in `research/01 Sources` (type source, publisher the team), and the Data pull note names the filing behind every actual cell.
- Each module's memo is filed into the vault before its section is built: a source note for every source it cites and an atomic note for every number or dated fact it uses that is not a workbook number, each `needs-verification` until a person checks it (the "File the memo into the vault" prompt in `PROMPTS.md`). If asked to build a section from a memo that has not been filed, say so and file it first.
- Never invent a figure, a date, a URL, or a quote. Say "I could not find this" instead.
- Each number in the Knowledge Bank carries a tier: Reported (from a filing or dataset as published), Derived (calculated from reported numbers, show the formula), or Estimate (a judgment call, name who made it and why).

## Working style
- Before changing files, state the plan in plain English and wait for a go-ahead.
- Explain what you did in plain English after each task. The user is new to this tool.
- Keep site copy short: forty words or fewer per block, headlines of eight words or fewer.
- No em-dashes in anything you write.
- The Module 3 redesign follows `skills/site-design/DESIGN.md` (with `skills/design-taste/SKILL.md`); the brief lists the files it may change. On any later design request ("polish", "make it look better"): read both, change styling and layout only, and keep every section one screen tall. Always within this site's rules: plain HTML, CSS, and JavaScript, no packages, no frameworks, no motion libraries, Google Fonts only; never a number, a section id, a nav label, a Fact, the content of `content.js`, or `site/data/`. Propose directions and wait for a pick before changing files. The one exception is the "Trim for presenting" prompt (end of Module 5, again in Module 7): it may shorten words in `content.js` (headlines, ledes, block text, so-whats, Fact labels) to the brief's "Say less" budgets, never a number or a Fact's value, tier, source, or note.

## Git
- On "sync" or "sync the project": run `git pull` in this folder, then summarize what changed in plain English. Stop on any conflict and explain it.
- On "wrap up" or "wrap up the session": add today's rows to `AI Log.md` (show them first), regenerate `site/data/financials.js` if the workbook changed, rerun `python3 scripts/build_vault.py` if any note in `research/` changed (from Module 3 on), commit with a one-line message that describes the change (never an empty or generic message; the user relies on it in GitHub Desktop), then run `git push`. Report the push as done only if the command succeeded. If it fails for authentication, say so plainly and tell the user to open GitHub Desktop and click Push origin; never ask for a password or token.
- Never force-push. Never delete a branch. Never commit files larger than 20 MB.
- If a push fails, tell the user to click Push origin in GitHub Desktop. That is normal on a Mac that has not stored a git credential.

## Safety
- Never ask for or store passwords, tokens, or API keys. Nothing in this repo is secret.
- Only public filings and public data.
- Never commit a vendor's raw data export (FactSet, Bloomberg, Capital IQ) or paste its table into a note. The repo and the site are public and those licenses forbid republishing bulk data. The export stays in `research/01 Sources/_files`, which git ignores for spreadsheets; commit the source note, the cells typed into the workbook, and their rows in the Data pull note, nothing more.
